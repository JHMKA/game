我认为**不改 HiSparse 算子本身，仍然有比较大的优化空间**。从当前 SGLang 源码看，HiSparse 已经把 host/device KV 管理集中在 `HiSparseCoordinator`，并且有独立 `prefetch_stream` 和 miss-plan 数据结构，因此很适合在 coordinator 和 scheduler 层做优化，而不用碰([GitHub][1])([GitHub][1])

我最推荐把它做成下面这个组合：

> **Temporal Predictive Prefetch + I/O-aware Scheduling + Adaptive Prefetch Budget**

它仍然保持：

```text
Full KV → CPU
Hot KV  → GPU
Top-k   → Sparse Attention
```

完全不改变 HiSparse 的计算结果，只是尽可能让需要的 KV **在真正被 top-k 选中之前，就已经进入 GPU**。

---

## 1. 当前 HiSparse 为什么会慢

当前最麻烦的路径是：

```text
               Decode step t
                    │
                 Indexer
                    │
                 Top-K
                    │
           ┌────────┴────────┐
           │                 │
          Hit               Miss
           │                 │
           │             CPU DRAM
           │                 │
           │               PCIe
           │                 │
           └──────────────→ GPU
                             │
                         Attention
```

如果 miss 的 KV 必须等：

$$
CPU\rightarrow GPU
$$

传完才能继续 attention，那么：

$$
T_{\text{decode}}
=
T_{\text{compute}}
+
T_{\text{miss-IO}}
$$

论文的 no-I/O oracle 也表明，HiSparse 剩余的主要额外成本就是 host-device I/O，而不是它的 resolution 逻辑本身。([arXiv][2])

所以真正应该做的是：

$$
T_{\text{decode}}
=
\max(T_{\text{compute}},T_{\text{IO}})
$$

而不是简单优化 CUDA operator。

---

# 2. 第一项：跨 Token 的预测预取

我觉得这是最值得尝试的一项。

现在 HiSparse 已经支持一种 prefetch，但主要利用的是：

> 同一个 decode step，不同 layer 之间共享 index。

源码明确写的是 `shared-index prefetch`：

```text
Anchor layer
    │
    ├── 得到 top-k
    │
    ├── 记录 miss plan
    │
    └──────────────┐
                   │ async
Layer N compute    │ CPU → GPU
                   │
                   ↓
             shared layer N+1
```

([GitHub][1])

但我们可以再利用另外一种局部性：

## Temporal locality

LLM 连续生成：

```text
token t
token t+1
token t+2
```

三个 query 通常不会完全无关。

假设：

```text
step t:

top-k =
[3, 8, 25, 91, 102, 108, 351, ...]
```

而：

```text
step t+1:

top-k =
[3, 8, 25, 92, 102, 108, 351, ...]
```

如果两步 top-k 有比较高的重叠，那么我们不必等：

```text
step t+1 Indexer
        ↓
      miss
        ↓
CPU → GPU
```

而是在 step t 结束以后直接预测：

```text
S(t+1) ≈ S(t)
```

提前搬。

---

# 3. 不要简单地把上一轮 Top-K 全搬过去

这会浪费 PCIe。

我会做一个 **Top-K Stability Predictor**。

对每个 request、每个 anchor layer 记录最近几步：

$$
S_t,S_{t-1},S_{t-2}
$$

首先计算 top-k 保留率：

$$
R_t=
\frac{|S_t\cap S_{t-1}|}{K}
$$

例如：

```text
K = 2048

两次相同 = 1700

R = 1700 / 2048
  = 83%
```

这意味着：

> 上一轮 Top-K 对下一轮具有很强预测能力。

反过来：

```text
R = 20%
```

说明索引变化很剧烈。

这种 request 就没必要浪费 PCIe 进行 aggressive prefetch。

---

# 4. 自适应决定“预取多少”

因此增加：

```text
prefetch_budget
```

例如：

$$
P_t=P_{\max}\cdot R_t
$$

假设：

```text
top_k = 2048
Pmax  = 1024
```

### 稳定 request

```text
R = 0.9

prefetch ≈ 922 KV
```

### 不稳定 request

```text
R = 0.2

prefetch ≈ 205 KV
```

甚至：

```text
R < 0.15

prefetch = 0
```

这样避免出现一个很典型的问题：

```text
错误预测
   ↓
搬了一堆 KV
   ↓
PCIe bandwidth 被占用
   ↓
还挤掉 GPU 里的 hot KV
   ↓
真正 Top-K 来了以后又 miss
```

也就是所谓的：

> **prefetch pollution**

---

# 5. 再进一步：不要只看上一轮

可以维护一个很轻量的历史热度。

例如：

$$
Score(i)=
1.0I(i\in S_t)
+
0.5I(i\in S_{t-1})
+
0.25I(i\in S_{t-2})
$$

于是：

```text
token 100
最近三次都被选中
Score = 1.75

token 523
只有这一次被选中
Score = 1.0
```

优先预取：

```text
高 score
    ↓
GPU
```

而不是：

```text
全部上一轮 Top-K
    ↓
GPU
```

这里甚至**不需要 indexer 给你 probability / score**。

只记录：

```text
top-k token IDs
```

就够了。

所以不用改 indexer。

---

# 6. 最重要的一点：预测错了也不会改变模型结果

这是这个方案比较漂亮的地方。

我们只是提前改变 KV 的：

> residence / placement

并没有改变：

```text
Indexer Top-K
Attention
KV value
```

比如我们预测：

```text
A B C D
```

实际需要：

```text
A B E F
```

那么：

```text
A B → Hit

E F → 原始 HiSparse miss-resolution
       CPU → GPU
```

最终计算的依然是：

```text
A B E F
```

所以：

$$
Output_{\text{optimized}}
=
Output_{\text{HiSparse}}
$$

属于 **exact optimization**。

# 7. 第二项：Two-Microbatch I/O Overlap

不过单纯 temporal prefetch 还不够。

真正比较大的优化可以是：

> 把 decode batch 分成两个 microbatch。

例如原本：

```text
Batch = 64 requests
```

改成：

```text
A = 32 requests
B = 32 requests
```

然后：

```text
时间 ──────────────────────────────→

Compute stream:

        Compute A
                    Compute B
                                Compute A
                                           Compute B


Prefetch stream:

        Prefetch B
                    Prefetch A
                                Prefetch B
```

即：

```text
              GPU Compute
                  │
                  │
           ┌──────┴──────┐
           │             │
        Batch A        Batch B
           │             │
           │             │
           ↓             ↓

t1:   Compute A  ||  Prefetch B

t2:   Compute B  ||  Prefetch A(next)

t3:   Compute A  ||  Prefetch B(next)
```

于是原来的：

$$
T=C+I
$$

理想情况下变成：

$$
T\approx\max(C,I)
$$

---

# 8. 举一个很直观的数字

假设目前：

```text
GPU compute      = 800 μs
HiSparse H2D IO  = 400 μs
```

现在：

$$
T=800+400=1200\mu s
$$

如果实现 overlap：

```text
Compute
████████████████████

IO
██████████
```

重叠：

```text
Compute
████████████████████

IO
██████████
```

就有可能变成：

$$
T\approx800\sim900\mu s
$$

而不是 1200 μs。

换句话说，TPOT 理论上可能从：

```text
1.2 ms

↓

~0.85-0.95 ms
```

当然实际提升多少需要实测 PCIe 利用率和 overlap window。

# 9. 但 Two-Batch Overlap 本身不能作为主要创新

这一点要特别提醒你。

当前 SGLang HiSparse roadmap 已经明确列出了：

> “Support TwoBatch Overlap to hide IO latency”

同时也已经在做：

> IndexShared based IO prefetch + compute overlap。([GitHub][3])

因此如果你以后是想：

> **基于这个东西做一个论文工作**

我不会把：

```text
async memcpy
+
two batch
```

当核心贡献。

它更适合作为你的 baseline optimization。

# 10. 第三项才是比较有研究价值的：I/O-aware Scheduler

这是我更看好的方向。

传统 scheduler 主要考虑：

```text
token 数
batch size
KV capacity
```

但是对于 HiSparse，两个 batch 即使：

```text
batch size = 32
```

实际耗时也可能完全不一样。

### Batch A

```text
cache hit rate = 95%
```

只需要搬：

```text
很少 KV
```

### Batch B

```text
cache hit rate = 50%
```

需要大量：

```text
CPU → GPU
```

于是：

```text
Batch A = compute bound
Batch B = IO bound
```

传统 scheduler 看不出来这个区别。

---

# 11. 给每个 request 建一个 I/O cost

例如维护 EMA：

$$
m_r^{(t)}
=
\alpha m_r^{(t-1)}
+
(1-\alpha)\frac{\text{miss}}{K}
$$

那么预测这个 request 下一步产生的 H2D：

$$
IO_r
=
m_rK\times Bytes_{KV}\times L
$$

其中：

* \(m_r\)：预测 miss rate
* \(K\)：top-k
* \(Bytes_{KV}\)：每个 KV entry 大小
* \(L\)：相关 sparse layers 数量

于是 scheduler 不只是看到：

```text
request 1
request 2
request 3
```

而会看到：

```text
Req A   predicted IO = 2 MB
Req B   predicted IO = 18 MB
Req C   predicted IO = 3 MB
Req D   predicted IO = 16 MB
```

---

# 12. 然后做 High-I/O / Low-I/O 配对

不要：

```text
Batch 1:
B + D + F + H
全是 high miss
```

因为这样瞬间把 PCIe 吃满。

而是：

```text
Batch 1:

High IO
Low IO
High IO
Low IO
```

让每个 batch 的：

$$
\sum IO_r
$$

尽量接近。

例如：

```text
before

Batch A = 80 MB
Batch B = 15 MB
Batch C = 75 MB
Batch D = 20 MB
```

变成：

```text
after

Batch A = 46 MB
Batch B = 48 MB
Batch C = 49 MB
Batch D = 47 MB
```

这样能够减少：

```text
PCIe burst
↓
transfer queue
↓
tail latency
```

---

# 13. 可以再设置一个 PCIe Budget

例如实时测出：

$$
BW_{\text{H2D}}=50GB/s
$$

允许一个 decode step 最多用于 IO：

$$
T_{IO,target}=300\mu s
$$

则：

$$
Budget
=
50GB/s\times300\mu s
\approx15MB
$$

scheduler 就控制：

$$
\sum_{r\in Batch}PredictedIO_r
\leq Budget
$$

变成：

> **I/O-aware continuous batching**

这比单纯改变 `device_buffer_size` 有意思得多。

# 14. 第四项：自适应 Prefetch，不是越多越好

这里还可以增加一个 feedback controller。

实时记录：

```text
prefetch_hit_rate
miss_rate
H2D bandwidth
GPU utilization
prefetch waste
```

定义：

$$
Accuracy_{prefetch}
=
\frac{\text{prefetched and actually used}}
{\text{prefetched}}
$$

例如：

```text
prefetch accuracy > 80%
```

说明预测很好：

```text
prefetch_budget ↑
```

如果：

```text
accuracy < 30%
```

就：

```text
prefetch_budget ↓
```

如果 PCIe 已经：

```text
> 85% utilization
```

也应该：

```text
prefetch_budget ↓
```

因此形成：

```text
               runtime statistics
                       │
        ┌──────────────┼─────────────┐
        ↓              ↓             ↓
    miss rate     prediction       PCIe BW
                    accuracy
        │              │             │
        └──────────────┼─────────────┘
                       ↓
             Prefetch Controller
                       ↓
                prefetch budget
```

# 15. 与 `device_buffer_size` 联动

当前 HiSparse 配置里本身有：

```text
top_k
device_buffer_size
host_to_device_ratio
swap_in_block_size
```

官方示例甚至给的是：

```text
top_k = 2048

device_buffer_size = 6144
```

([GitHub][4])

源码中对于长序列，请求会受到这个 `device_buffer_size` 上限约束，并维护 per-request 的设备 buffer 和 LRU 元数据。([GitHub][1])

所以我们还可以做一个**启动时 auto tuner**：

```text
top_k = 2048

候选：
4096
5120
6144
7168
8192
```

分别跑几十个 decode step。

测：

$$
Cost(B)
=
TPOT(B)+\lambda Memory(B)
$$

自动选择：

```text
device_buffer_size*
```

而不是人工写死：

```bash
"device_buffer_size": 4096
```

这一项实现非常简单，可以作为工程补充，但不适合作为主要创新。

# 16. 最后整个系统会变成这样

我建议最终架构：

```text
                    Request
                       │
                       ↓
              ┌────────────────┐
              │ IO-aware       │
              │ Scheduler      │
              └───────┬────────┘
                      │
                Batch A / B
                      │
          ┌───────────┴────────────┐
          │                        │
          ↓                        ↓
    Compute Stream            Prefetch Stream
          │                        │
          │                 Temporal Predictor
          │                        │
          │                  predicted Top-K
          │                        │
          │                    CPU → GPU
          │                        │
          └───────────┬────────────┘
                      ↓
                HiSparse Cache
                      │
                  Indexer
                      │
                  actual Top-K
                      │
             ┌────────┴────────┐
             ↓                 ↓
            HIT               MISS
             │                 │
             │          Original HiSparse
             │            CPU → GPU
             └────────┬────────┘
                      ↓
              Sparse Attention
```

**最底下的：**

```text
Indexer
HiSparse resolve kernel
Sparse attention operator
```

全部不用改。

你改的是：

```text
HiSparseCoordinator
Scheduler
CUDA stream/event orchestration
少量历史 metadata
```

而 SGLang 当前确实已经把 HiSparse coordinator 独立出来，并在 model runner 初始化时将 `device_buffer_size`、`host_to_device_ratio` 等交给 coordinator，非常适合从这里插入机制。([GitHub][5])

### 1. 不要每生成一个 token 都急着完成 D2H backup

HiSparse 现在不仅有：

```text
CPU → GPU
swap-in
```

还有另一条容易被忽略的路径：

```text
GPU → CPU
eager backup
```

因为新生成 token 的 KV 最开始是在 GPU 上，但完整历史最终需要存在 host KV pool。

当前源码确实会调用 `_eager_backup_previous_token()`，使用独立 `decode_backup_stream` 把 KV 写回 CPU。更关键的是，在提交下一次 backup 前，代码里有：

```text
self.wait_for_pending_backup()
```

随后当前 stream 会等待 `_backup_done_event`。([GitHub][2])

所以实际上可能出现：

```text
Decode t
   │
   ├── Compute
   │
   └── D2H backup t
             │
             │ 还没结束
             ↓
Decode t+1
   │
   ├── 想提交 backup t+1
   │
   └── wait_for_pending_backup
             ↓
           等待
```

即使你的 H2D：

```text
hit rate = 98%
```

这里仍然可能造成 latency。

这和你前面“hit 很高，但还是慢”的现象是高度相关的。

---

### 2. 可以改成 Multi-buffered Backup Pipeline

不要只有：

```text
1 个 pending backup
```

而是维护一个很小的 ring：

```text
Backup slot 0
Backup slot 1
Backup slot 2
Backup slot 3
```

例如：

```text
Decode t
Compute ███████████████

D2H(t-1)       ███████


Decode t+1
        Compute ███████████████

D2H(t)                ███████


Decode t+2
                Compute ███████████████

D2H(t+1)                     ███████
```

只有当：

```text
backup queue 满
```

才真正 wait。

原本：

$$
T_t=C_t+W_{backup}
$$

希望变成：

$$
T_t\approx C_t
$$

而 backup 在后面异步排队。

这个**不是 prefetch**。

Prefetch 优化：

$$
CPU\rightarrow GPU
$$

Backup Pipeline 优化：

$$
GPU\rightarrow CPU
$$

两个方向完全不同。

---

### 3. 再做 Deferred Backup：最近几个 token 暂时别写回 CPU

还可以进一步加一个：

> **Recent-KV GPU Window**

例如最近 4 个 token：

```text
t
t-1
t-2
t-3
```

先固定放在 GPU：

```text
GPU recent ring
┌─────┬─────┬─────┬─────┐
│ t   │t-1  │t-2  │t-3  │
└─────┴─────┴─────┴─────┘
```

不需要马上：

```text
GPU → CPU
```

等积累成一个小 batch：

```text
t-4
t-5
t-6
t-7
```

再一次性 backup。

这有两个好处。

第一，减少 transfer launch 次数。NVIDIA 自己的 CUDA Best Practices 也明确建议：**多个小 host-device transfer 尽可能合并成较大的 transfer**，因为每次传输都有固定开销。([NVIDIA Docs][3])

第二，可以：

```text
每 token 一次 D2H
```

变成：

```text
每 N token 一次 D2H
```

例如：

$$
N=4
$$

理论上 transfer setup/scheduling 次数降低约 4 倍。

当然必须保证：

> 一个 KV 在真正被 GPU buffer 淘汰之前已经完成 host backup。

所以需要：

```text
Recent protected region
        +
Deferred backup queue
```

共同保证 correctness。

---

### 4. H2D 和 D2H 不应该拥有相同优先级

这是另一个我很看好的点。

HiSparse decode 里实际上有两种 I/O：

```text
Critical IO:

CPU → GPU
miss KV
↓
Attention 必须等它
```

以及：

```text
Background IO:

GPU → CPU
新 token backup
↓
未来才需要
```

这两者的重要性完全不同。

如果同时发生：

```text
           PCIe
           │
 H2D ──────┤
 D2H ──────┤
 backup ───┤
 other ────┤
```

却没有 QoS，那么后台 backup 会和关键 swap-in 抢 PCIe / memory bandwidth。

SGLang 今年其实也有类似的 QoS RFC，指出 latency-critical KV transfer 与后台 cache write 共用传输资源时，需要区分优先级。([GitHub][4])

因此可以设计：

```text
          IO Controller

        ┌───────┴────────┐
        ↓                ↓
Critical H2D       Background D2H
priority = HIGH     priority = LOW
        │                │
        └───────┬────────┘
                ↓
              PCIe
```

简单策略就是：

```text
if H2D miss pending:
    pause / throttle backup
else:
    drain backup queue
```

不需要改 HiSparse kernel。

---

### 5. I/O-aware Scheduler 比单纯 Prefetch 更适合高并发

假设现在：

```text
Req A miss = 5%
Req B miss = 6%
Req C miss = 30%
Req D miss = 28%
```

普通 scheduler 可能：

```text
Batch 1:
C D

Batch 2:
A B
```

于是 Batch 1：

```text
CPU → GPU
████████████████████████████
```

瞬间把 host bandwidth / PCIe 打满。

更好的方式：

```text
Batch 1:
A C

Batch 2:
B D
```

让每个 batch 的：

$$
IO_{batch}
=
\sum_r MissBytes_r
$$

比较均衡。

甚至可以直接设一个：

$$
IOBudget
$$

例如：

$$
PredictedH2D(batch)<20MB
$$

再允许 request 加入 batch。

这相当于：

> scheduler 不只知道“这个请求需要多少 token”，还知道“这个请求下一步大概会制造多少 PCIe 流量”。

这也是我认为**论文价值比单纯 prefetch 更高**的一点。

---

### 6. NUMA-aware host KV placement 很值得检查

这个属于实现成本低、但经常非常有效的优化。

HiSparse host KV 使用 pinned memory；当前源码里也明确提到了 pinned host pool。([GitHub][2]) CUDA 官方文档也明确指出，page-locked/pinned memory 是高效异步 H2D 的基础。([NVIDIA Docs][5])

问题是：

> pinned ≠ 一定物理上离 GPU 最近。

双路 CPU 服务器可能是：

```text
NUMA 0
 CPU0
   │
 PCIe
   │
 GPU0


NUMA 1
 CPU1
```

如果 GPU0 的 host KV 被实际分配在：

```text
NUMA1
```

访问可能变成：

```text
GPU0
 ↑
PCIe
 ↑
CPU0
 ↑
UPI / intersocket
 ↑
NUMA1 memory
```

而不是：

```text
GPU0
 ↑
PCIe
 ↑
NUMA0 memory
```

于是你就可能看到：

```text
hit rate 很高
miss 很少

但是：

每次 miss 极其昂贵
```

所以一定要测：

```text
nvidia-smi topo -m
numactl --hardware
```

然后把：

```text
scheduler CPU
host KV pinned memory
GPU
```

尽可能绑到同一 NUMA domain。

NVIDIA 甚至提供了专门的 PCIe bandwidth diagnostic 来检查 H2D/D2H bandwidth、latency 和 link downtraining。([NVIDIA Docs][6])

---

### 7. 还有一个经常被忽略的：消除隐式 synchronization

你现在应该特别检查 profiler 里的：

```text
cudaStreamSynchronize
cudaDeviceSynchronize
cudaEventSynchronize
aten::_local_scalar_dense
```

SGLang 自己今年就出现过一个性能 bug：GPU tensor 被 Python 当 slice index 使用，触发 `_local_scalar_dense`，进而产生 `cudaStreamSynchronize`，直接破坏 overlap。([GitHub][7])

这种问题非常可怕，因为：

```text
H2D 本来只需要 50 us
```

但：

```text
CPU sync
 ↓
等待整个 stream
 ↓
200 us
```

你最后会误以为：

> “HiSparse swap 很慢。”

实际上慢的是：

> **同步 barrier。**

所以我建议你的 profiling 里一定单独统计：

$$
T_{\text{sync}}
$$

而不能只测：

$$
T_{\text{H2D}}
$$

---

## 如果是我现在给你选研究方向

结合你已经发现：

> **hit 很高，但是 latency 仍然很大**

我会把优先级从之前的“预测预取”稍微调整。

最值得先验证的是：

```text
              HiSparse latency
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
   H2D miss       D2H backup    Sync
        │           │           │
        │           ↓           ↓
        │      Backup Pipeline  Remove bubble
        │
        ↓
 IO-aware Scheduler
```

其中我现在最看好的组合是：

$$
\boxed{
\text{Deferred Batched Backup}
+
\text{Critical-I/O QoS}
+
\text{I/O-aware Scheduling}
}
$$

因为它和 prefetch 的故事完全不同：

> **Prefetch 是猜未来需要什么；这个方案是不猜任何东西，直接重新组织 HiSparse 已经必然发生的数据搬运。**

这样有一个很大的优势：**没有预测错误、没有 prefetch pollution，而且完全保持 exactness。**

尤其是当前源码里 `wait_for_pending_backup()` 这一段，我觉得非常值得你先 profile。它现在明确存在单个 pending backup 的 event dependency。([GitHub][2]) 如果你的实验显示很多 decode step 都在这里形成 bubble，那么“**multi-buffered deferred KV backup**”会比跨-token预测预取更干净，也更容易先做出一个可量化的结果。
